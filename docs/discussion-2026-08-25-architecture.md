# Macaronic 架构讨论记录（2026-08-25）

> 状态：顶层架构、衔接策略、跨块类型一致性检查均已收敛；待定项集中在本文件末尾「待定项」一节。

## 一、定位：构建工具，不是执行器

输入混合语言脚本 → 切分为各语言脚本 → 生成 shell 驱动按期调用各子程序。

```text
foo.mac（混合源文件）
   │ parse：按块标记切分 → [{lang, code}, ...]
   ▼
emit：每块落成独立文件 + 生成驱动脚本
   ├── build/stage1.py     (python 块)
   ├── build/stage2.sh     (bash 块)
   └── build/run.sh        (驱动：顺序调用 + 管道衔接)
```

Bridge 复杂度归零，驱动本身是 shell，衔接格式天然是 stdout→stdin。两层：切块、拼驱动。

错误定位：任一块失败时，报错映射回 `.mac` 源文件行号（生成文件中的错误行换算回源位置），不直接暴露 `build/stageN.ext`。

## 二、同类工具调研

无确切同款；最接近的是 Org Babel（Emacs，代码块 + `:var` 传结果 + `:session` 会话）、
.NET Interactive（多语言变量共享，2026-04 已归档）、knitr（语言引擎注册表）、
Runme（可执行 Markdown，shell 中心）、marcel（仅 shell+Python 混合交互 shell）。

差异化定位：**脚本文件（非文档/notebook）+ 命令行构建（非交互）+ 块间自动衔接（非手动 export）**。

可借鉴：knitr engine 注册表、org-babel :var 显式传参、.NET Interactive 值级共享。

## 三、块间衔接方式

局限（单一管道）：单一字节流、无结构化、纯文本降级、不可断点重跑、不可分支、错误边界模糊、无法反向通信。

替代（按复杂度升序）：中间文件、环境变量、命令参数、命名管道 FIFO、共享 JSON 文件、unix socket 消息、数据库/消息队列、FFI 嵌入/常驻解释器。

结论：MVP 用管道，管道的字节流承载二进制 POD 数据（直接字节交换，见第四节），减少文本转换开销；第一步升级 JSON 文件/共享状态；session/kernel 级别不自研，真有需求做 .NET Interactive 格式兼容。突破点的关键是去掉"线性"或"匿名"。

## 四、可衔接的数据类型

分两档：

### 直接字节交换（POD，约定布局）

- int/u32/i64
- float/double (IEEE 754)
- bool (0/1)
- char/byte/enum(底层宽度)
- 定长数组 (numpy ndarray 即 C 数组布局)
- C struct（仅 POD 成员，同 ABI 内）

### 需要序列化

- string/字节数组（长度前缀）
- map/hash/dict
- 树/图/链表
- 对象/多态（类型 tag）
- 资源句柄

注意：用户偏好最常用 **int/float/bool/定长数组/string(长度前缀)/定长 struct(同 ABI)**——完备。序列化可以传任何类型，但 JSON 等格式传的是「值在格式词汇表里的投影」；函数/身份/资源句柄永远传不了。要传任意类型需 schema/IDL + 代码生成（protobuf/flatbuffers）。

## 五、设计边界（防滑线）

边界在「谁定义计算」：

| 层 | 性质 |
|---|---|
| 块切分标注 | 格式约定，非语言 |
| 驱动生成 | Makefile 同类，非语言 |
| 数据契约 schema | 接口定义，非语言 |

危险区：块级控制流（if/loop）、自研类型语义、跨语言对象行为定义——只要有一层进入运行语义就滑向新语言。

防滑线：**类型由双方各自的真语言定义，macaronic 只传送字节，不判语义**；控制流留在 shell 驱动里。

## 六、跨块变量类型一致性检查（编译期）

已定案：不做运行时反射，不做静态检查器集成，只做编译期轻量静态检查。

语义：`head` 区（`#!mac` 块）集中声明跨块变量类型（int/float/str/bool），各块内做类型推导（见「块内类型传播」一节），再把传播结果与头部声明比对，冲突即报错；块内局部变量不要求声明；传播不出即通过。

定位：`x` 是**检查标签**，不绑定运行期实体。数据仍由块代码自己写/读管道（二进制 POD 字节），macaronic 不搬运、不序列化、不注入——只比对各块对同一名字的类型声明与头部契约是否一致。

```text
#!mac
[contract]
x = "int"
y = "float"

#!python
print(x)
```

`#!mac` 块的内容是 TOML（标准库 `tomllib` 解析），`[contract]` 表声明跨块变量契约。块标记语法由此统一：所有块都是 `#!lang`，head 只是 lang=mac 的特殊块。

检查逻辑（编译期内嵌）：`[contract]` 表是锚点，逐块跑推断，命中表内名字则比对。

- 推断种子：显式类型声明（`int x;` 无需初值）、字面量赋值（`x = 5`）、函数返回类型签名——详见「块内类型传播」
- 函数调用赋值：`x = compute()` 若函数有显式返回类型签名 → 解析；无签名或无类型关键字的调用 → 静默通过。`int x = compute()` 由显式声明直接解析（关键字 `int` 定义类型，右值忽略）
- 静态检查器集成（mypy/go types/clang）已排除：原理上只能查单语言单文件，无法跨块，且集成成本高
- 运行时反射已排除：需要每语言 wrapper，违背「编译期完成」

## 七、块内类型传播（编译期推断引擎）

**目的**：从变量声明和函数签名中的类型出发，通过替换和简单运算传播类型。传播只在单个代码块内进行，不跨块；其最终产出用于与头部契约表（上一节）比对，以确认跨段变量的类型一致。

把「显式声明」「字面量赋值」「函数签名」统一收敛为一个机制：**符号表 + 顺序求值替换**。

### 机制

维护一张「名字 → 类型」符号表，按语句顺序求值化简：

```text
x: int = 0     → 表 {x: int}
y = x          → 查表 → 表 {y: int}
z = y * 2      → 规则 int ∘ int → int → 表 {z: int}
a = compute()  → 若 def compute() -> int → 表 {a: int}（函数调用点按变量替换，继续传播）
b = a + 1      → int ∘ int → 表 {b: int}
c = unknown_f() → 无签名 → 停，静默通过
```

### 种子（初值来源，三档）

1. 显式类型声明：`int x;` `var x int` `let x: i32` `x: int = 0`
1. 字面量赋值：`x = 5` / `x = 5.0` / `x = "str"` / `x = True`
1. 函数返回类型（签名）：`def f() -> int` / `func f() int` / `int f();` / `fn f() -> i32`

### 能力边界

| 能 | 不能 |
|---|---|
| `y = x` 别名传播 | if/loop 内赋值（控制流不进，留在 shell） |
| `z = y + 1` 同类型运算 | 跨类型运算语义（`int + str` 各语言不同，不判） |
| 链式 `a = b = c` | 函数体推导（只认签名，不认实现） |
| 后写覆盖先写（顺序求值） | 遮蔽（块内局部同名变量，需作用域栈，暂不做） |
| 显式返回类型的函数调用按值替换继续传播 | 无返回签名 / 需要读函数体（如 `def g(): return h()` 链） |
| 有签名的调用参与运算传播（`a + 1`） | 函数参数值类型推导（只有签名，无法推参数内部） |

暂停点：遇到控制流分支 / 跨类型运算 / 内部同名遮蔽 → 停止传播，静默通过（宁可漏报不误报）。

跨块仍由头部契约表作锚点——本机制是块内的，边界是外部的。

### 与防滑线的关系

符号表 + 替换是「机械替换」，不是「语义解读」：不解释 `+` 的语义、不读函数体、不定义跨语言对象行为。仍在防滑线之内。

## 八、语言支持：核心注册表，不做插件

定案：语言引擎全部内置在核心，用一个注册表 dict 挂接；每个语言一个 handler（类或函数），负责识别声明语法、类型传播规则、生成驱动命令。新增语言 = 新增一个文件 + 注册一行。

```python
engines = {
    "python": PythonEngine(),
    "shell":  ShellEngine(),
    "go":     GoEngine(),   # 含 build 步骤
}
```

插件/动态加载机制（Python entry-points、Go plugin、子进程协议）全部推迟到出现第三方语言贡献者时再引入——handler 已是注册表，届时包一层入口扫描即可，不返工。
